# Участие в разработке

Благодарим за интерес к `verilator-mcp`. Проект рассчитан на инженеров FPGA/ASIC и разработчиков средств верификации. Мы приветствуем воспроизводимые ошибки, проверенные примеры логов и реализации, которые улучшают работу нескольких MCP-клиентов.

## Перед изменением

1. Проверьте существующие issues и аналогичные реализации, не переписывайте устойчивый механизм без причины.
2. Опишите наблюдаемое поведение, версии ОС и EDA-продукта, ожидаемый и фактический результат.
3. Для существенного изменения публичного интерфейса согласуйте контракт в issue.
4. Не публикуйте корпоративные исходники, лицензии, пути к закрытым проектам, полные журналы с секретами и проприетарные базы производителя.

## Локальная разработка

```bash
uv sync
uv run python -m unittest discover -s tests -v
uv run python -m compileall -q src tests
```

Если доступ к PyPI ограничен, тесты доменной логики можно выполнять обычным `python`, установив `PYTHONPATH=src`. Конфигурацию настоящего MCP-клиента проверяйте отдельно, не называйте тестом соединения компиляцию Python-файлов.

## Требования к PR

- Одна целостная задача; понятные риски, обратимость и границы доступа.
- Типизированные входные/выходные данные, ограниченные размеры и время выполнения.
- Никаких произвольных shell-команд, незапрошенных скачиваний и скрытых внешних сетевых вызовов.
- Тесты успеха, отказа, неправильных путей/входных данных и тайм-аутов для каждого нового инструмента.
- Изменения поведения сопровождаются обновлениями README, TOOL_CONTRACT и CHANGELOG.
- Ошибки EDA отличайте от `NOT_RUN`, `NOT_SUPPORTED`, `TOOL_MISSING` и отказа MCP.

## Стиль и коммиты

Используйте Python с аннотациями типов и читаемыми именами. Человеко-читаемые инженерные комментарии и документация — на русском; названия публичных API и терминов сохраняются на английском. История Git по Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`). Обязательное ревью для изменений, запускающих внешние процессы.

## Права на вклад

Внося изменения, участник подтверждает право распространять их по Apache-2.0. Исключите из PR код и материалы с несовместимыми лицензиями. Вопросы безопасности — по [SECURITY.md](SECURITY.md), а не через публичные issues.
