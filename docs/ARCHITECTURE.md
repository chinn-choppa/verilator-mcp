# Архитектура

## Роли компонентов

```text
MCP-клиент (Codex / Claude / OpenCode / др.)
           |
      MCP stdio
           |
  verilator_mcp.server
     |           |
   runtime    diagnostics
   (поиск)    (разбор логов)
           |
 Verilator (в будущих версиях)
```

Текущий сервер не запускает внешний EDA-продукт. Добавление исполнителя допускается только после выделения узких, проверяемых операций, а не универсального `run_command`.

## Почему отдельный репозиторий

- Сервер развивается и выпускается независимо от навыков и установщика `agent-dev-toolkit`.
- `agent-dev-toolkit` впоследствии может устанавливать определённую версию из доверенного реестра; обратной зависимости нет.
- Публичный интерфейс MCP должен работать с любым совместимым клиентом, не только с Codex.
- Повторно используемый код между тремя EDA-адаптерами можно извлекать **после** появления как минимум двух проверенных сценариев.

## Изоляция и воспроизводимость

По умолчанию локальный stdio, без внешнего HTTP и сетевых запросов. Входные и выходные каталоги будущих EDA-операций должны задаваться явно. Каждая операция обязана фиксировать tool/version, конфигурацию сборки, полный exit status, артефакты и статус `NOT_RUN` при пропуске реального выполнения.

## Недопустимые сокращения

Ни `--version`, ни `tools/list`, ни успешная компиляция Python не подтверждают корректность RTL. Обнаруженный бинарник ещё не означает проверенную конфигурацию лицензии. Не объявлять testcase `PASS` только по отсутствию ошибок в текстовом выводе, если не установлен надёжный критерий завершения.

## Предметный сценарий

Проектный source manifest → lint → сборка → запуск тестбенча → анализ assertion/coverage → Wavepeek/wave-mcp при необходимости.
