# Запуск симуляций и результат верификации (M2)

[English](SIMULATION.en.md) · [Сборка](BUILD.md) · [Безопасность](../SECURITY.md)

`simulation_run(build_id, timeout_seconds=30, seed=1)` запускает **только** исполняемый файл, ранее созданный успешным `build_run`. Клиент не может указать произвольную программу, путь, shell, свободные аргументы симулятора или дополнительные сценарии.

## Безопасный контракт входа

- `build_id` — только `build-` + 32 шестнадцатеричных символа. Каталог сборки разрешается строго внутри операторского корня артефактов.
- Перед запуском проверяются `request.json` и `result.json`: `build_status=PASS`, `executed=true`, соответствие конфигурации, источников и ожидаемого имени бинарника.
- Бинарник пересчитывается по SHA-256 непосредственно перед запуском и повторно после завершения. При несовпадении запуск не выполняется или выдаётся `BINARY_CHANGED`.
- Seed — целое **1..2147483647**; `0` запрещён, поскольку Verilator выбирает для него недетерминированный seed. Тайм-аут: **1..180** секунд.
- В бинарник передаются только `+verilator+seed+N` и `+VERILATOR_MCP_TOKEN=<одноразовый токен>`. Параметры MCP не позволяют добавлять произвольные plusargs.
- Каждый запуск создаёт изолированный `sim-<uuid>` с запросом, результатом и ограниченными журналами (до 64 КиБ на поток).

## Когда можно вернуть PASS

Необходимо **одновременно**: реальный exit code `0`, отсутствие наблюдаемого `$fatal`/ошибки assertion, полный (необрезанный) журнал, строка `VERILATOR_MCP_PASS:<токен данного запуска>` и наблюдаемое сообщение Verilator `Verilog $finish`. Маркер должен печататься **только после всех самопроверок тестбенча**.

Пример использования токена в SystemVerilog:

```systemverilog
string token;
initial begin
    if (!$value$plusargs("VERILATOR_MCP_TOKEN=%s", token))
        $fatal(1, "missing token");
    // Проверки DUT...
    if (test_failed)
        $fatal(1, "test failed");
    $display("VERILATOR_MCP_PASS:%s", token);
    $finish;
end
```

Пример является фрагментом: сигнал `test_failed` должен определяться конкретным самопроверяющимся тестбенчем.

`run_status`: `PASS`, `RUN_FAIL`, `TIMEOUT`, `FINISHED_UNVERIFIED`, `EXIT_ZERO_UNVERIFIED`, `INCOMPLETE`, `BINARY_CHANGED`, `ARTIFACT_INVALID`, `NOT_RUN`.

`verification_verdict`: `PASS`, `FAIL`, `INCONCLUSIVE`, `NOT_RUN`. Отдельно возвращаются `finish_observed`, `fatal_observed`, `pass_marker_observed`, `exit_code`, `timed_out`, `duration_ms`, `seed`, `build_id`, `run_id`, `binary_sha256`, версии инструментов и ссылки на локальные артефакты.

Код возврата `0` **без маркера** даёт лишь `INCONCLUSIVE`. Тайм-аут — явный `FAIL` по watchdog, но не обязательно дефект DUT. `$fatal` и ненулевой код — `FAIL`.

## Границы доверия

Успешный маркер не является криптографическим доказательством правильности RTL: его может напечатать неверно написанный тестбенч. Автор проекта отвечает за качество самопроверок. Проверяется только реальный текст и завершение процесса; значения сигналов сервер **не придумывает**.

Verilator преимущественно двухсостояниевый. Успешная симуляция не заменяет четырёхсостояниевые проверки, особенно для X/Z, сбросов, CDC и неопределённых состояний. Memory, CPU и доступ к ФС не изолируются ОС-средствами; используйте VM или контейнер для потенциально недоверенного RTL/бинарников. Двоичные файлы и записи сборки в каталоге артефактов принадлежат доверенному локальному оператору. От подмены записей пользователем с теми же правами криптографической защиты нет.

## Приёмка

```bash
VERILATOR_MCP_RUN_INTEGRATION=1 uv run python -m unittest discover -s tests -p 'test_simulation_integration.py' -v
```

Интеграция на Ubuntu проверяет `PASS`, `$fatal`, `INCONCLUSIVE` и timeout на открытых RTL-фикстурах. Отмена ожидающей задачи отдельно проверяется unit-тестом процесса. Windows/MSYS2 Verilator: `NOT_RUN`, пока не выполнен реальный независимый прогон.
